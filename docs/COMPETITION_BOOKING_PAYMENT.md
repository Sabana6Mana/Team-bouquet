# MATCHPOINT 경진대회 체육관 예약·결제 MVP

## 한 줄 결론

대회에서는 전국 체육관을 실시간으로 예약한다고 과장하지 않고, **강남 배드민턴 데모 체육관
2~3곳의 운영자 관리 슬롯**을 대상으로 `시간 합의 → 예약 요청 → 운영자 확인 → 테스트 결제
→ 예약 확정`의 한 사이클을 완성한다.

공공 API는 체육관을 찾고 보여 주는 용도로 사용한다. 공개된 API만으로 모든 시설의 실시간
잔여 시간과 예약 생성까지 통합할 수 있다고 가정하지 않는다. 실제 출시 전에는 시설 제휴나
각 공식 예약 채널과의 별도 연동이 필요하다.

## 대회 MVP 범위

### 포함

- 강남구 배드민턴 체육관 2~3곳의 데모 슬롯
- 경기 참가자들의 시간 합의 후 체육관·시간 선택
- 동일 슬롯 중복 예약을 막는 10분 임시 선점(HOLD)
- 운영자가 예약 가능 여부와 금액을 확인하는 화면
- 대표자 1명의 PG 테스트 결제
- 서버의 주문번호·금액 검증과 결제 승인
- 예약 확정 번호, 이용 시간, 체육관, 결제 상태 표시
- 운영자 취소 시 예약 취소와 테스트 결제 취소 상태 표시
- 모든 예약 상태 변경을 남기는 감사 로그

### 제외

- 전국 모든 공공·민간 체육시설의 실시간 재고 연동
- 비제휴 시설 웹사이트의 자동 예약이나 스크래핑
- 실제 카드 출금과 실제 체육관 정산
- 여러 참가자의 개별 결제·부분 미납·부분 환불
- 체육관별 세금, 수수료, 증빙, 정산 대사 자동화
- 우천, 감면 자격, 지역주민 할인 등 시설별 모든 예외 규칙

테스트 화면에는 항상 `테스트 결제 · 실제 금액이 출금되지 않습니다`를 표시한다. 시연용
예약번호도 `MP-DEMO-...`처럼 실제 예약번호와 구분한다.

## 왜 이 범위가 현실적인가

- 공유누리의 공개 API 목록은 체육시설·상세 자원의 **조회** 기능을 제공하지만 공개 예약 생성
  API는 안내하지 않는다.
- 서울시 공공서비스예약 공개데이터도 예약은 공식 사이트에서 직접 해야 하고, 데이터 연계
  시차가 있을 수 있다고 안내한다. 공개데이터의 `예약 가능` 표시는 결제 직전의 확정 재고로
  취급하면 안 된다.
- 실제 시설마다 `즉시 결제`, `신청 후 승인`, `현장 결제`, 환불 기한이 다르다. 일부 시설은
  예약자 본인 이용과 양도 금지까지 명시한다.
- 따라서 비제휴 체육관을 MATCHPOINT 운영자 개인 계정으로 대신 예약하는 방식은 확장하기
  어렵고 시설 규정과 충돌할 수 있다. 비제휴 시설은 사용자가 공식 채널에서 직접 예약하고
  MATCHPOINT가 확인하는 편이 안전하다.
- 카카오 로그인과 카카오페이는 별도 제품이다. 카카오 로그인을 완성했다고 결제가 가능한 것은
  아니며, 카카오페이 실제 온라인 결제는 별도 가맹점 제휴가 필요하다.

대회에서는 실제 출금 없이 요청·인증·승인·취소를 검증할 수 있는 토스페이먼츠 테스트 환경을
권장한다. 카카오페이는 계약 후 발급되는 상점용 테스트 키가 필요하므로 대회 일정에는 토스
테스트 결제가 더 예측 가능하다.

## 권장 사용자 흐름

1. 매칭 참가자들이 경기 시간을 합의한다.
2. 앱은 선택 시간에 맞는 데모 체육관과 운영자 관리 슬롯을 보여 준다.
3. 방장이 슬롯을 선택하면 서버가 10분 동안 `held` 상태로 원자적으로 선점한다.
4. 예약은 `예약 확인 중`이 되고 운영자가 슬롯·요금·시설 규칙을 확인한다.
5. 이용할 수 없으면 결제 없이 대체 슬롯을 제안하고 HOLD를 반환한다.
6. 이용 가능하면 예약을 `결제 대기`로 바꾸고 서버가 확정 금액과 주문번호를 만든다.
7. 대표자 한 명이 테스트 결제를 진행한다.
8. 서버는 결제 전에 저장한 `order_id`, 예약 ID, 금액과 PG가 돌려준 값을 비교한다.
9. 값이 같을 때만 PG 승인 API를 호출하고 결제 키를 저장한다.
10. 결제 승인이 끝나면 슬롯과 예약을 하나의 트랜잭션으로 `예약 확정` 처리한다.
11. 취소 시 예약 규칙을 확인하고 PG 취소를 먼저 확정한 뒤 예약 상태와 슬롯을 갱신한다.

`가결제`라는 표현은 사용하지 않는다. 일반 PG가 카드 승인 보류와 나중 매입을 당연히 지원한다고
가정하지 말고, 대회 MVP는 **운영자 가용성 확인 후 테스트 결제 승인** 순서로 설계한다.

### 비용 부담 방식

대회 MVP는 대표자 1명이 전체 대관료를 결제한다. 화면에는 `총 20,000원 · 4명 기준 예상
5,000원/인`처럼 참고 금액만 보여 준다. 여러 사람이 각자 결제하면 한 명 미납, 결제 도중 HOLD
만료, 부분 취소와 환불 문제가 함께 생기므로 이번 범위에서는 제외한다.

실출시에서 1/N 비용 분담을 제공하더라도 `시설 예약 결제`와 `참가자끼리 정산`은 별도 상태로
관리해야 한다. 참가자 간 송금 완료 여부를 확인할 수 없는 단순 정산 링크를 예약 확정의 조건으로
사용하면 안 된다.

## 최소 데이터 모델

실제 컬럼명은 기존 스키마 규칙에 맞추되 다음 책임은 분리한다.

| 테이블 | 핵심 필드 | 역할 |
| --- | --- | --- |
| `venue_booking_sources` | `venue_id`, `source_type`, `booking_url`, `terms_note` | `demo`, `partner`, `external_link` 출처와 공식 예약 경로 관리 |
| `venue_slots` | `venue_id`, `court_ref`, `starts_at`, `ends_at`, `price`, `status`, `hold_expires_at`, `version` | 예약 가능 시간, 가격, HOLD와 확정 상태 관리 |
| `reservation_requests` | `match_id`, `slot_id`, `payer_id`, `status`, `external_reference`, `checked_by`, `checked_at` | 매치와 실제 예약 요청의 수명주기 관리 |
| `payments` | `reservation_id`, `provider`, `test_mode`, `order_id`, `amount`, `payment_key`, `status`, `approved_at` | 결제 요청·승인·취소 기록 관리 |
| `reservation_events` | `reservation_id`, `actor_id`, `event_type`, `payload`, `created_at` | 운영자 조치와 상태 변경 감사 로그 |

### 반드시 지킬 제약

- 같은 체육관·코트의 겹치는 시간에는 활성 슬롯 예약이 하나만 존재해야 한다.
- 매치 하나에는 활성 예약 요청이 하나만 존재해야 한다.
- 슬롯 HOLD 생성과 기존 예약 검사는 같은 DB 트랜잭션에서 실행한다.
- 만료 작업은 `hold_expires_at`이 지난 `held` 슬롯을 다시 `open`으로 돌린다.
- `order_id`는 전역 고유값이며 같은 승인 요청을 재시도해도 결제가 한 번만 처리되어야 한다.
- 결제 금액은 브라우저 값을 믿지 않고 서버에 미리 저장한 금액과 비교한다.
- 결제 승인과 예약 확정이 중간에 끊기면 재처리할 수 있도록 결제 상태를 먼저 조회한다.
- PG 시크릿 키는 서버에만 두고 `VITE_` 환경변수나 클라이언트 번들에 넣지 않는다.
- 사용자는 자신의 예약만 읽고, 상태 전이는 서버 RPC/함수와 권한 있는 운영자만 수행한다.

## 상태 전이

### 슬롯

```text
open ──선택──> held ──결제 완료──> booked
                 ├─HOLD 만료/거절──> open
                 └─운영 중단──────> blocked

booked ──정상 취소──> open 또는 blocked
```

### 예약 요청

```text
requested → checking → payment_pending → confirmed
    │           │              │              │
    └──────────> rejected      ├────────────> expired
                cancelled <────┴──────────────┘
```

- `confirmed`는 PG 승인과 슬롯 `booked` 처리가 모두 끝난 경우에만 사용한다.
- `payment_pending` 상태에서 결제창만 성공한 것을 예약 확정으로 표시하면 안 된다.
- 이미 승인된 결제가 있는데 예약 확정 트랜잭션만 실패했다면 결제 조회 후 확정을 재시도하거나
  자동 취소한다.

### 결제

```text
ready → authenticated → done → cancelled
  │           │
  └───────────┴──────> failed
```

앱의 상태명과 PG의 원본 상태를 모두 저장한다. PG 상태 변경 웹훅은 중복 수신을 전제로
멱등하게 처리하고, 시연에서는 승인·취소 응답까지 직접 확인한다.

## 60~90초 시연 시나리오

| 시간 | 시연 내용 | 심사위원에게 보일 핵심 |
| --- | --- | --- |
| 0~15초 | 두 사용자의 배드민턴 매칭과 19:00 시간 합의 | 매칭 결과가 예약으로 자연스럽게 이어짐 |
| 15~30초 | 지도에서 강남 데모 체육관과 19:00 슬롯 선택 | 거리, 시간, 가격을 한 화면에서 비교 |
| 30~40초 | `예약 확인 중` 표시 후 운영자 화면에서 사용 가능 승인 | 실제 시설별 확인 단계를 숨기지 않음 |
| 40~65초 | 대표자가 20,000원 토스 테스트 결제 | 실제 출금 없는 PG 요청·인증·승인 흐름 |
| 65~80초 | `예약 확정`, `MP-DEMO-...`, 5,000원/인 예상 비용과 알림 표시 | 매칭부터 예약 확정까지 완결된 경험 |
| 선택 10초 | 운영자가 취소하고 결제·슬롯이 취소 상태로 변하는 모습 | 실패·취소까지 고려한 백엔드 |

시연 계정과 데이터는 미리 준비하고, 네트워크 실패에 대비해 같은 상태 전이를 보여 주는 녹화
영상을 준비한다. 단, 녹화와 실시간 시연 모두 테스트 결제임을 숨기지 않는다.

## 실출시 3단계 로드맵

### 1단계: 공식 예약 채널 연결

- 공공데이터와 공유누리로 시설을 탐색한다.
- 사용자가 시설 공식 사이트에서 직접 예약하고 직접 결제한다.
- MATCHPOINT에는 예약번호·화면 증빙을 등록하고 운영자가 확인한다.
- MATCHPOINT가 돈을 받거나 시설에 송금하지 않으므로 초기 정산 위험이 가장 작다.

### 2단계: 소수 제휴 체육관 재고 연동

- 시설 관리자 포털에서 제휴 체육관이 슬롯·가격·휴무를 직접 관리한다.
- MATCHPOINT가 슬롯 HOLD, 결제, 취소를 처리한다.
- 예약자 명의, 환불 기준, 수수료, 사고 책임, 개인정보 처리, 정산 주기를 계약으로 정한다.
- API를 제공하는 시설은 웹훅과 예약 ID를 연동하고, API가 없는 시설은 관리자 포털을
  원장으로 사용한다.

### 3단계: 다수 시설과 자동 정산

- PG 지급대행 계약을 맺고 체육관을 셀러로 등록한다.
- 사업자·계좌 검증, 본인인증 또는 KYC, 정산 보류와 지급 실패 재처리를 구현한다.
- 결제·취소·지급대행 웹훅, 대사 작업, 세금·증빙과 분쟁 운영 체계를 갖춘다.
- 전국 확장은 이 단계에서 제휴 범위와 데이터 품질이 검증된 지역부터 진행한다.

일반 단건결제로 돈을 받은 뒤 개인 계좌에서 체육관마다 수동 송금하는 구조를 제품의 기본
정산 방식으로 삼지 않는다. 실제 출시 전에는 PG사, 시설 파트너, 회계·법률 전문가에게 계약과
자금 흐름을 확인한다.

## 주요 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 공개데이터와 실제 재고의 시차 | 공개데이터를 탐색용으로만 쓰고 확정 전 제휴 재고 또는 공식 채널 재검증 |
| 두 사용자의 동일 슬롯 동시 선택 | DB 트랜잭션, 시간 중복 제약, 10분 HOLD와 만료 작업 |
| 운영자 대리 예약이 시설 규정과 충돌 | 비제휴 시설은 예약자 직접 예약, 제휴 시설만 계약된 방식으로 운영 |
| 시설 확인 전에 결제되어 환불 발생 | 운영자 확인 후 결제 요청, 실패 시 결제 없이 대체 슬롯 제안 |
| 결제 승인 후 예약 확정만 실패 | 결제 조회 기반 재처리 또는 자동 취소, 감사 로그 기록 |
| 여러 참가자 중 일부 미결제 | 대회는 대표자 1인 결제, 개별 분담은 후속 기능으로 분리 |
| 중복 승인·취소 | 고유 주문번호와 멱등키, 웹훅 이벤트 중복 처리 |
| 시연을 실서비스처럼 오인 | 모든 데모 슬롯·예약번호·결제 화면에 테스트 표기 |

## 발표 문구

> 공공 API는 체육시설 탐색에 활용하고, 예약 확정은 제휴 재고 또는 시설의 공식 예약 채널로
> 검증합니다. 이번 시연에서는 제휴 상황을 가정한 운영자 관리 슬롯과 테스트 PG를 이용해
> 매칭, 시간 합의, 예약 요청, 승인, 결제, 취소까지의 트랜잭션을 검증했습니다.

피해야 할 표현:

- `전국 모든 체육관의 실시간 예약이 이미 가능합니다.`

- `결제금은 자동으로 각 체육관에 정산됩니다.`
